Key guarantees

ConcernMechanism
No oversellingRows locked in deterministic order, plus conditional update WHERE available_qty >= :qty, plus a database check constraint.
No partial multi-product reservationAll lines reserved in one transaction; any shortfall rolls everything back.
No duplicate ordersIdempotency-Key header with a unique constraint: same payload returns the original order, a different payload returns 409.
No lost eventsOutbox row is written in the same transaction as the business change and marked published only after Kafka acknowledges.
No duplicate effectsConsumer effect and the processed_events marker commit together.
Bounded retriesFailures recorded with attempts, error and timestamps; redelivered after 2 s; dead-lettered after 3 attempts.
Consistent lifecycleTransitions guarded under row locks; a cancelled order can never be confirmed or fulfilled by a late event or payment.

Order lifecycle

PENDING_PAYMENT --payment succeeded / confirm--> CONFIRMED --fulfil--> FULFILLED
       |
       +--cancel--------------------> CANCELLED   (reservations released)
       +--expire (30 min, automatic)-> CANCELLED   (reservations released)
Rejected purchase attempts. A request rejected for insufficient stock does not become an order. Every request outcome (accepted, rejected, replay, key conflict) is stored in order_requests and shown on the Order Requests page, so 50 attempts against 10 units appear as 10 orders and 50 recorded requests.

5. Event flow and failure handling

  1. A business change (order created, confirmed, cancelled, fulfilled, expired; payment succeeded, failed, timed out, refunded) writes an outbox_events row in the same database transaction.
  2. The scheduled publisher reads pending rows every 2 seconds and sends them to Kafka: orders to order-events, payments to payment-events, keyed by aggregate id.
  3. Only after Kafka acknowledges is the row stamped published_at and published_via = KAFKA. A failed or timed-out send increments attempt_count, stores last_error and is retried on the next poll.
  4. The consumer checks processed_events. A duplicate is skipped and audited. Otherwise it applies its effect and writes the marker in one transaction.
  5. If processing fails, the attempt is recorded in event_failures and Kafka redelivers after 2 seconds. A later success marks the failure recovered.
  6. After 3 failed attempts the event is marked DEAD_LETTERED, forwarded to <topic>.DLT, and the offset is committed so the partition keeps moving. It can be retried manually from the dashboard or API.

If the application crashes after Kafka acknowledged but before published_at is written, the event is published again on restart. Delivery is therefore at-least-once, and the idempotent consumer makes the repeat harmless.

8. Known limitations

  • Designed for a single backend instance; several instances would need row-level claiming in the outbox poller.
  • The consumer records an audited processing step; a real downstream worker would plug into the same idempotent consumer.
  • Unit prices come from the order request, as products have no price list.
  • Failure simulation is in-memory, explicitly armed and audited, and exists for demonstrations only.
